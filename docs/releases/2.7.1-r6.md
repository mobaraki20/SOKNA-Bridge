# SOKNA Bridge 2.7.1-r6

Delivery correctness hotfix for false `existing-bubble` detection.

## Live failure fixed

The live diagnostics proved that:
- semantic command detection succeeded;
- the Agent executed the command and returned a real RESULT;
- the Extension received `result.received`;
- RESULT delivery started;
- but the prior `SOKNA-V2-STATUS` accepted event carried the same `commandId`;
- the visibility detector searched IDs across page text and falsely treated that STATUS as the RESULT bubble;
- delivery was marked `existing-bubble` although no RESULT had been posted.

## r6 behavior

- Existing-bubble detection is envelope-type aware.
- `SOKNA-V2-RESULT` is matched only against RESULT envelopes using `payload.id`.
- `SOKNA-V2-STATUS` is matched only against STATUS envelopes using `payload.eventId`.
- `commandId` can no longer prove that a RESULT is visible.
- Free-text ID substrings can no longer prove delivery.
- When user-role message roots are available, visibility checks are scoped to user turns; otherwise the adapter falls back to exact envelope parsing in page text for compatible third-party ChatGPT panels.
- Delivery diagnostics now retain the last type-aware visibility decision.

## Regression coverage

The terminal/delivery suite now requires all of the following:
- a STATUS accepted event with `commandId=cmd-123` must NOT satisfy a future RESULT with `id=cmd-123`;
- once the actual RESULT envelope appears, it must be recognized;
- the same rule applies to `ok:false` error RESULTS;
- arbitrary page text containing matching `id` or `commandId` substrings must not count as delivery;
- existing terminal STATUS behavior remains independent and correct.
