# SOKNA Bridge 2.7.1-r4

Installer recovery hotfix for systems that still have an older SOKNA runtime listening on the configured agent port without enough modern ownership state for the r3 installer to stop it.

## Live failure fixed

The r3 installer could fail during `initialize` with exit code 10 when an authenticated older SOKNA 2.x PowerShell agent was still listening on the migrated port (commonly 8766) but its PID/ownership evidence was missing or belonged to the older bootstrap layout.

## r4 behavior

- Detects candidate endpoint settings from the current or legacy SOKNA config.
- Authenticates the live endpoint with the existing SOKNA token and requires it to identify itself as a SOKNA 2.x agent.
- Correlates the endpoint to a PowerShell/pwsh `agent.ps1` process using its command line and config path.
- Refuses to stop unknown, ambiguous, non-PowerShell, or non-SOKNA processes.
- Stops the uniquely proven legacy runtime, waits for the endpoint to become available, preserves/migrates config, then continues initialization.
- Records recovery evidence in `state/install-preparation.json`.

## Regression coverage

Full Windows acceptance deliberately starts a legacy SOKNA agent, deletes its legacy `agent.pid`, leaves the authenticated endpoint running, and then launches Setup. The acceptance requires:
- the exact old process to exit;
- migrated port/token to be preserved;
- recovery PID/port/source evidence to match;
- the new 2.7.1 runtime to pass health;
- reinstall, repair, upgrade, rollback, support-bundle, and uninstall acceptance to remain green.

## Release safety

- Pull requests targeting `release/2.7.1` run the full Windows validation profile before merge.
- Publication remains gated to pushes on `release/2.7.1` after validation succeeds.
- The immutable release tag is `sokna-agent-2.7.1-r4`.
- Existing r1/r2/r3 tags are never moved.
