# SOKNA Bridge 2.7.1-r7

Transport-state and semantic-recovery hotfix for the r6 live incident.

## Confirmed live failures fixed

### 1. Submitted RESULT resend loop
A RESULT could be submitted once, leave the composer, fail conversation-bubble ACK detection, and enter `awaiting_conversation_ack`. r6 treated that record like ordinary pending work on retry, so the full composer/submit path could run again indefinitely.

r7 introduces an explicit durable delivery state machine:
- `queued`
- `submitted_awaiting_ack`
- `acknowledged`
- `delivery_uncertain`

Once a payload is known to have been submitted, automatic retries are visibility-only ACK polls. The payload is never reinserted into the composer automatically.

### 2. Unbounded ACK waiting
ACK polling is bounded by both a deadline and a maximum poll count. If the RESULT bubble cannot be confirmed, the record moves to `delivery_uncertain` / Needs Action instead of looping forever.

### 3. Reload / re-arm replay
Legacy r6 records whose last wait reason is `awaiting_conversation_ack` are migrated fail-safe to `submitted_awaiting_ack`. Reload/re-arm therefore performs visibility reconciliation and cannot blindly re-submit those records.

### 4. Queue starvation
A `delivery_uncertain` record is no longer retry-eligible, so newer queued results can continue. ACK polls also back off between visibility checks.

### 5. Semantic proof loss after reload
When intake proof is established, background now stores the challenge-bound proof with the armed conversation. On content reload for the same conversation and same challenge, Semantic Adapter 2.1.1 restores that proof instead of resetting trust to `proof-incomplete`.

The active bridge nonce is still required. Conversation mismatch, challenge mismatch, user-role markers, and unsafe editable contexts remain fail-closed.

## Safety preserved

- User drafts are never overwritten.
- Unknown or ambiguous result visibility never triggers a blind resend after submission.
- Existing type-aware RESULT/STATUS envelope matching from r6 remains enforced.
- Uncertain delivery requires operator attention instead of risking duplicate chat messages.

## New regression coverage

- submitted RESULT + delayed ACK => one submit, visibility-only polling
- ACK never appears => bounded transition to `delivery_uncertain`
- legacy r6 awaiting-ACK record => fail-safe submitted-state migration
- uncertain record => no automatic resend
- manual recovery => visibility check only
- semantic proof restore after content reload
- restored proof still requires the active nonce
- existing STATUS-vs-RESULT false-positive regression remains covered
